# step5 · 自测答案（对照 `step5-多线程流水线/self-test.md`）

## 一、复述题要点

1. 架构：采集线程 →（写）最新帧槽 → 结果线程（put/get 池）→（写）显示槽 → 显示线程；
   池 = 3 worker / 3 NPU 核；`maxPending=3` 给出延迟上界。
2. 三根柱子：
   - **深拷贝**：坏的=浅拷贝入队 → 症状=随机错乱 → 证据 T1（不一致 0）；
   - **背压**：坏的=无界队列 → 症状=延迟无上界 → 证据 T2（accept=2/reject=28/实际执行 2）；
   - **锁外等待**：坏的=抱锁等 future → 症状=put() 被堵 → 证据 T3（0.078 ms vs 旧 ≈30 ms）。
3. `cv_.wait(lk, pred)`；醒来重查 → 防**虚假唤醒**时对空队列 `front()`（§1.5 修的就是这个 UB）。
4. ① 延迟≈单帧+~1ms；② 显示解耦（A≈D、B≈C）；③ 拒收=采集−结果（"只处理最新"）；
   ④ 106 vs 125 差额=喂料间隙（1ms 睡眠量化 + 槽 ~4.9ms 节拍 + 采集抢 CPU；**归因留 B10**）。

## 二、追问链（闭合点）

- 链 A：Mat 头复制但 data 共享 → worker 读到的是"主线程下一帧" → 时序决定对错（所以"随机"）→
  T1 把"提交后立刻覆写"变成必然覆盖，把随机 bug 变成计数为 0/非 0 的**可判定实验** →
  只修深拷贝不修背压：延迟先塌（无上界）。
- 链 B：帧队列=旧帧排队→延迟无界；实时系统宁愿丢"过期帧"；$L=\lambda W$ → maxPending≈L+余量；
  get 阻塞 ⇒ 在途=1 ⇒ 池退化；采集慢（41.7fps 级）但**池与槽解耦后**吞吐由池决定 → 106 fps。

## 三、变式题参考答案

**变式 1**：3 个 worker 各绑一核；其余线程（采集/显示/结果壳）**只做 CPU 侧活**，不碰 NPU；
若想进一步压榨：每核 2 线程交叠 CPU 准备（实测 41.9→44.6 fps 的机理），但预期总量仍 ≤~125 fps。
**变式 2**：60fps：maxPending 可放宽（延迟预算 16.7ms）、显示间隔随意、后处理可加重；
**不能动**：3 核配置本身（球速跟踪要求端到端延迟小，帧率不是唯一约束——见 00 §4）。
**变式 3**：imshow 阻塞几十 ms → 结果线程被拖慢 → 吞吐跌向"imshow 周期"、延迟抖动增大；
验证：横向对照"显示写盘（当前）vs 直接 imshow"，看吞吐与延迟 min/max（B8-3 的 A/C/D 就是这套设计）。
