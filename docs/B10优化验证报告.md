# B10 优化验证报告（mppjpegdec / RGA / DMA-BUF 零拷贝）

> **定位**：这是 B10（Ch07 调优方向）的**可行性验证记录**。2026-09-23 受用户指派：
> **只做「可行性分析 + 板端验证 + 实测数据」**，不改动主工程任何功能行为；
> 具体实现由用户日后在**自己的新工程**中完成。
>
> **一句话结论**：三项技术**在板子上都存在、都能跑通**；但在**当前 640×480@109.5fps 的结构下，
> 没有一项能带来明显收益**——当前「OpenCV 软解 + CPU letterbox」已经是够用且便宜的选择。
> 它们的真正价值是**为将来更高分辨率 / 更省 CPU 的「全硬件采集链」铺路**，且本次把该链路的
> 两个关键坑（**dmabuf 缓存一致性**、**首次 set_io_mem 不生效**）提前踩出来了。

---

## 0. 结论总表（先看这个）

| # | 优化项 | 可行？ | 当前值得做？ | 关键实测数据 | 建议 |
|---|---|---|---|---|---|
| 1 | **mppjpegdec 硬解**（替代 OpenCV 软解） | ⚠️ 半可行 | ❌ 不做 | 硬解 0.42ms/帧 vs 软解 1.01ms/帧（都远远低于 9.1ms 帧间隔）；OpenCV 直通**收不到帧**、经 videoconvert **16.9ms/帧**（比现路径还慢） | 保持现状；将来做"自研采集链"时才启用 |
| 2 | **RGA 硬件预处理**（替代 CPU letterbox） | ✅ 可行且正确 | ❌ 不做 | 摆放 RGA 0.30ms vs CPU 0.07ms；缩放 RGA 0.99ms vs CPU 0.35ms（**小分辨率 CPU 快 3~4 倍**） | 当前分辨率无收益；高分辨率/多路/需喂 dmabuf 时再考虑 |
| 3 | **DMA-BUF 零拷贝喂 NPU** | ✅ 可行 | 🟡 可选 | 接口全通；每帧省 **0.18ms**（输入拷贝 0.105ms 实测）；**首次 set_io_mem 不生效**（用法已找到） | 新工程若要压延迟可做，务必按 §4.3 的用法 + 哈希自检 |

**一句话记账**：现结构每帧预算 9.1ms（@110fps）里，**解码只占 1ms 以内、且被帧节拍完全掩盖**——
这就是"硬解没收益"的根本原因。**只有当单帧预算被压到 1~2ms 级别（更高分辨率/更高帧率）时，这三件事才开始值钱。**

## 2. E1：mppjpegdec 硬解链路验证

### 2.1 纯解码吞吐（3290 帧文件流，已摊薄启动开销）

| 链路 | 墙钟 | **每帧** | 备注 |
|---|---|---|---|
| 软解 `jpegdec`（gst→I420） | 3.313 s | **1.01 ms** | libjpeg-turbo 单线程 |
| 软解 PIL（→RGB，独立实现交叉验证） | 0.752 s（329帧） | **2.29 ms** | 含 RGB 转换 |
| **硬解 `mppjpegdec`** | 1.379 s | **0.42 ms** | 峰值 ≈ 2380 帧/秒 |
| 硬解 → **BGR 直出** | 1.415 s | **0.43 ms** | 颜色转换在硬件内完成，免费 |
| 硬解 → **DMABuf 输出** | 1.407 s | **0.43 ms** | 直接是 DMA 缓冲，免费 |
| 硬解 → `videoconvert` → BGR | 52.5 s（658帧） | **79.8 ms** ⚠️ | 见下方「异常记录」；appsink 实测同类链路 **16.9 ms** |

### 2.2 摄像头实时链路（v4l2src 600 帧，含 ~0.4s 启动）

| 链路 | 墙钟 | 换算 | 结论 |
|---|---|---|---|
| 仅采集（不解码） | 5.87 s | ≈102 fps | |
| 采集 + 硬解 | 5.80 s | ≈103 fps | **解码耗时完全隐藏** |
| 采集 + 硬解 + BGR | 5.80 s | ≈103 fps | 转换也免费 |

### 2.3 关键实验：能不能让 OpenCV 用上硬解帧？（**答：不能**）

| 模式 | 结果 |
|---|---|
| M0 基线：OpenCV 直接开 V4L2（现路径） | **read 9.14ms（min 7.96）| 109.4 fps** ✅ |
| M4 原始 MJPEG 直读（不解码） | **read 9.13ms（min 7.96）| 109.5 fps** ← 与 M0 **几乎相同** |
| M1 硬解直通 `mppjpegdec ! BGR ! appsink` | ❌ **0 帧**（OpenCV 收不到；`dma-feature=false` 也不行，`format=16` 变体直接 core dump） |
| M2 硬解 + `videoconvert` + appsink | ⚠️ 能读，但 **read 16.93ms → 59.1 fps**（比现路径**更慢**） |

**M0 vs M4 的洞察（本次最有价值的发现）**：
读原始 JPEG（不解码）与读解码后的 BGR **耗时几乎一样**（9.13 vs 9.14ms，min 都是 7.96）——
说明在实时流里，`read()` 主要由"等下一帧的节拍（8~9ms）+ V4L2 机制"决定，
**JPEG 解码本身根本没进关键路径**。这正是"换硬解没有收益"的直接证据。

### 2.4 E1 结论

1. **解码速度**：硬解 0.42ms 完胜软解 1.01ms——但两者都远低于 9.1ms 的帧间隔预算，**赢了也没用**。
2. **交付路径**：mppjpegdec 的输出是 **DMABuf 交付**——`fakesink` 能收（测吞吐），
   但 **OpenCV appsink 收不到**；`videoconvert` 能收但要 16.9ms（比软解整条路径还慢）。
   ⇒ 在"OpenCV 采集"这个框架里，**没有可用的接入点**。
3. **可行的替代路线只有"自研采集链"**（不进 OpenCV）：V4L2 → MPP → 下游直接吃 dmabuf（RGA/NPU），
   属于"重构"不是"优化"——按用户约定，**留到新工程**。

**异常记录（未复现，存疑）**：同一 videoconvert 链路曾测出 **79.8ms/帧**（两次正常值为 16.9 / 18.3ms）。
原因未查明（怀疑与协商到的中间格式有关）。⚠️ 此现象与既有"appsink 慢 3.7 倍"疑点相邻，**保持为卡片，不展开**。

## 3. E2：RGA 硬件预处理验证

> 测法：`tools/b10/e2_rga_probe.cc`（librga im2d，**系统头文件 /usr/include/rga**，1000 次取平均；
> 结果图 `/tmp/e2_A.jpg`、`/tmp/e2_B.jpg` 已目视 + 数值双重核对）

### 3.1 耗时数据

| 场景 | 朴素用法（每次 wrapbuffer） | **句柄版**（importbuffer 一次+wrapbuffer_handle） | CPU 对照 | RGA/CPU 比 |
|---|---|---|---|---|
| 640×480 → 640×640 摆放（=当前扫描场景） | 0.61 ms | **0.30 ms** | **0.07 ms**（copyMakeBorder） | 4.3×（更慢） |
| 1280×720 → 640×360 缩放+摆放 | 1.67 ms | **0.99 ms** | **0.35 ms**（resize+border） | 2.8×（更慢） |
| — | — | — | 每帧新建 dst 的 border：0.064 ms | — |

**正确性核对**（这个数字很关键）：
- 摆放 `imcopy`：**最大像素差 = 0（逐字节完全一致）** ✅
- 缩放 `imresize`：与 `cv::resize` 最大差 6（插值器差异，正常）✅

### 3.2 E2 结论

1. **功能完全可行、结果正确**（RGA 会把活干对，含"写进大缓冲的偏移位置"这种摆放）。
2. **小分辨率下 CPU 更快**（0.07 vs 0.30ms）——RGA 每次调用的固定开销 ≈ 0.2~0.3ms（ioctl+同步），
   640×480 这点数据量根本喂不饱它。**"硬件单元"≠"更快"，要按任务大小选。**
3. **用法提示**：`importbuffer_virtualaddr` 一次 + `wrapbuffer_handle` 循环复用，可以把开销砍半
   （0.61→0.30ms）；每次调用前 wrapbuffer 的"朴素写法"要避免。
4. **RGA 的真正用武之地**：高分辨率/多路时给 CPU 卸载；以及**喂 dmabuf 的下游**（它可直接读 dmabuf，不落 CPU 内存）——
   与 E3 组合才是它的主战场。

## 4. E3：DMA-BUF 零拷贝喂 NPU 验证

> 测法：`tools/b10/e3_dmabuf_probe.cc`
> （`/dev/dma_heap/system` 申请真 dma-buf → `rknn_create_mem_from_fd` → `rknn_set_io_mem` → 与标准 `rknn_inputs_set` 路径对比）

### 4.1 接口可用性（✅ 全通）

```
rknn_create_mem_from_fd: OK (mem=... virt=0x7f91b88000 fd=12 size=1228800)
set_io_mem(pass_through=1): ret=0        ← 接受
```

### 4.2 收益数据

| 项 | 值 |
|---|---|
| `rknn_inputs_set` 单独耗时（拷 1.2MB 用户内存→驱动） | **0.105 ms/次**（500 次平均） |
| 标准路径（inputs_set + run + outputs） | 22.60 ms/帧 |
| 零拷贝路径（run + outputs，无输入拷贝） | 22.42 ms/帧 |
| **每帧节省** | **≈ 0.18 ms（约 0.8%）** |

### 4.3 ⭐ 踩坑记录：**进程内第一次 `set_io_mem` 不生效**（重要，新工程必读）

| 测试 | 结果 |
|---|---|
| Z1：首次绑定 + 200 帧 | hash=`412fd565` ❌（与标准 `89b16505` 不一致；逐字节差异 73682/115200，max=255） |
| Z1b：原地再跑 1 帧 | 仍 `412fd565` ❌ |
| Z1c：**显式 cache 同步**后再跑 | 仍 `412fd565` ❌ |
| **Z1d：对同一个 mem 再调用一次 `set_io_mem`** | **hash=`89b16505` ✅ 与标准完全一致** ← 假说成立 |
| Z2：**新 dma-buf 重新绑定**（uncached / cached+sync 两种都试） | **均 `89b16505` ✅ 逐位一致** |

**结论与正确用法**：
1. 零拷贝链路**数据可以做到与标准路径逐位一致**（hash 相同）。
2. 但**首次绑定会被静默忽略**（模型读到的是默认缓冲，输出稳定但错误）——
   表现为"推理跑得好好的、耗时也正常，但结果就是不对"。**光看时间发现不了，必须做输出校验。**
3. **落地配方**：① 绑定后先跑一帧、与已知基准**哈希自检**；② 不一致就**重复绑定一次**（本次实测有效）；
   ③ cached heap 配 `DMA_BUF_IOCTL_SYNC`（写后 END|WRITE），或直接用 `system-uncached` heap；
   ④ 每帧只需 CPU 写一次数据（或用 RGA/MPP 直接写这块缓冲）。

### 4.4 E3 结论

- **可行 ✅**（接口、数据、性能全实测）；
- **收益 0.18ms/帧**（消除 0.105ms 的输入拷贝 + 少许开销）——对 22.5ms/帧的现状是"锦上添花"；
- **真正的意义**：与 MPP/RGA 组合成"**全程不落 CPU 内存**"的采集→推理链（见 §5），
  以及为更高分辨率/更高帧率时保留延迟头寸。

## 5. 给"新工程"的落地路线建议

> 全部为**建议**，不替用户实现。按优先级排序；当前结构下三项都"不做"也是合法结论。

| 优先级 | 条件 | 做什么 |
|---|---|---|
| 🥉 最低 | 想彻底压采集延迟 / 跑 720p@120 / 省 CPU 核 | E1 的自研采集链：`V4L2(MJPEG,MMAP) → MPP 硬解(出 dmabuf) → [RGA 或 CPU] letterbox → NPU 输入 dmabuf`；**接口全部已验证可用** |
| 🥈 中 | 新工程要"延迟头寸"、反对拷贝 | E3 零拷贝输入（`create_mem_from_fd`+`set_io_mem`），按 §4.3 配方用 |
| 🥉 最低 | 高分辨率 / 多路 / CPU 饱和 | E2 RGA 接管预处理（**别忘了句柄版**） |
| — | **维持现状** | 640×480@109.5fps 下当前链路健康（结果 96fps / 延迟 24.4ms），**没有任何一项是瓶颈** |

## 6. 复现命令清单（板子上）

```bash
# 前置：demo lock（锁频）；相机空闲
cd ~/myproj

# E1-a：解码链路对照（文件流 + 相机 + 目视图 + PIL 交叉验证）
bash tools/b10/e1_decode_matrix.sh

# E1-b：OpenCV 交付路径探针（M0 基线 / 直通 / videoconvert / 原始直读）
g++ -O2 -std=c++14 tools/b10/e1_appsink_probe.cc -o /tmp/e1_appsink_probe $(pkg-config --cflags --libs opencv4)
timeout 300 taskset -c 4-7 /tmp/e1_appsink_probe

# E1-c：硬解 vs PIL 逐像素核对（需先有 /tmp/b10_raw.bgr 与参考 jpg）
python3 tools/b10/e1_mpp_vs_pil_check.py /tmp/b10_raw.bgr ~/videos/cam_20260923_125232/frame_000000.jpg

# E2：RGA 摆放/缩放/CPU 对照 + 正确性
g++ -O2 -std=c++14 -I /usr/include/rga tools/b10/e2_rga_probe.cc -o /tmp/e2_rga_probe -lrga $(pkg-config --cflags --libs opencv4)
taskset -c 4-7 /tmp/e2_rga_probe

# E3：DMA-BUF 零拷贝（标准 vs 零拷贝 vs 首次绑定对照）
g++ -O2 -std=c++14 -I include tools/b10/e3_dmabuf_probe.cc -o /tmp/e3_dmabuf_probe \
    -L install/my_rknn_yolov5_demo_aarch64/lib -lrknnrt $(pkg-config --cflags --libs opencv4)
LD_LIBRARY_PATH=install/my_rknn_yolov5_demo_aarch64/lib taskset -c 4-7 /tmp/e3_dmabuf_probe \
    install/my_rknn_yolov5_demo_aarch64/model/RK3588/best.rknn
```
