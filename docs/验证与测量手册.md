# 附录 B · 验证与测量手册

> **本文档回答四个问题**：我们用的每一个测试/测量手段 ——
> **① 它是什么？ ② 它在验证什么？ ③ 数据怎么读？ ④ 它的边界在哪（测不出什么）？**
>
> 📌 **纪律**：每新增一个验证手段，就来本文件补一条。

---

## 本章目标

学完本章，你能：

1. 说清"验证过了"到底意味着什么，而不是靠"看起来没报错"
2. 掌握 10 种验证手段，知道各自的**成本**和**能力边界**
3. 看懂我们收集的每一组数据，知道它在回答什么问题
4. **避开 5 个已经踩过的测量陷阱**

---

## 4.0 核心思想：怎么才算"验证过了"

**"编译通过"和"结果正确"之间隔着一整个太平洋。**

验证分三个层次，**成本递增，可信度递增**：

| 层 | 问题 | 手段 | 可信度 |
|---|---|---|---|
| **L1 · 能跑起来吗** | 语法对不对？链接过不过？ | `check.ps1`、板子编译 | 只能证明"不是完全错的" |
| **L2 · 数值对得上吗** | 打印的数字和**手算期望**一致吗？ | 手算对照、统计量 | ⭐ 主力手段 |
| **L3 · 行为符合物理/业务预期吗** | 精度够吗？延迟稳定吗？ | 标注对比、A/B 实验 | 最终验收 |

**本章所有手段都服务于 L2 和 L3。**

> 🔑 **贯穿全章的一句话**：
> **"一个正确的环节，必然产生一个可预测的物理量。"**
> 找到那个量、手算出期望值、拿实测去对 —— 这就是验证的全部本质。

## 4.2 逐项详解

### V1 · `tools\check.ps1` —— 本地语法检查

| 项 | 说明 |
|---|---|
| **是什么** | PC 上用 MinGW 的 `g++ -fsyntax-only` 解析源码，**不链接、不生成二进制** |
| **验证什么** | 拼写错误、语法错误、漏 `return`、类型不匹配警告、lambda 捕获问题 |
| **成本** | **1 秒**（对比 sync 往返约 30 秒） |
| **怎么读** | `[OK]` 通过；报错行号 + 原因 |
| **边界** | ❌ 不能查链接错误（`undefined reference`）<br>❌ 不能查 POSIX 头（`uart.c` 的 `<termios.h>`）<br>❌ 工具链与板子不同（MinGW vs aarch64-gcc），个别警告可能不一致 |

**实战战绩**（它抓到的真实错误）：

| 错误 | 类型 |
|---|---|
| `pirntf` / `prinf` / `print` | 拼写 |
| `ret=%d\m"` | 错误转义序列 |
| 漏 `return 0;` | 未定义行为 |
| `int i` vs `uint32_t` | 符号性警告 |
| `binding reference of type 'cv::Mat&' to 'const cv::Mat'` | lambda 默认 `const` |
| `'deqnt' was not declared` | 定义名与调用名不一致 |

### V2 · 板子编译 + 安装

| 项 | 说明 |
|---|---|
| **是什么** | `sync.ps1` 在板子上跑 `cmake --build` + `cmake --install` |
| **验证什么** | 链接是否成功、真实工具链（aarch64-gcc 9.4）是否接受、架构是否正确 |
| **怎么读** | `[OK] 编译成功` / `[OK] 全部完成 🎉` |
| **边界** | ❌ 编译成功**完全不保证逻辑正确** |

> ⚠️ **重要**：编译失败时 `install\` 里放的是**上一次的旧二进制**。
> 别以为"跑出来的结果是新的" —— 一定要看清楚 sync 有没有走到 `[OK] 全部完成`。

**配套的构建产物验证**（在板子上，回答"这个 `-I` / `-l` / `-rpath` 是谁加的"）：

| 命令 | 看什么 |
|---|---|
| `cat build/CMakeFiles/xxx.dir/flags.make` | 编译选项（`-O3` / `-I` / `-D`） |
| `cat build/CMakeFiles/xxx.dir/link.txt` | 链接命令（`-l` / `-rpath`） |
| `readelf -d <exe> \| grep -iE 'rpath\|runpath'` | 二进制里的 RPATH |
| `file <exe>` | 架构（aarch64 / x86_64） |
| `ldd <exe>` | 动态库能否找到 |

### V3 · 手算期望值 —— ⭐ **最强的验证手段**

| 项 | 说明 |
|---|---|
| **是什么** | 用数学/物理**提前算出**某个量应该是多少，再和实测对比 |
| **验证什么** | 数值是否正确（不只是"有输出"） |
| **成本** | 人脑几分钟 |
| **怎么读** | **偏差应该小到可以解释**（浮点误差、标注误差、模型误差） |
| **边界** | 需要你理解这一层的数学原理 —— 这也正是"学习"的价值 |

**本工程用过的 4 个手算案例**：

| # | 算的是什么 | 公式 | 期望值 | 实测 | 偏差 |
|---|---|---|---|---|---|
| 1 | 输出字节数 | `size = ∏dims × sizeof(INT8)` | 18×80×80=**115200** | 115200 | **0** ✅ |
| 2 | 反量化区间 | `real = (q+128)/255` | `[-128,127]→[0,1]` | min=0.0000,max=1.0000 | **0** ✅ |
| 3 | letterbox 参数 | `scale=min(640/W, 640/H)`<br>`pad=(640-new)/2` | vb1: `0.5`, `(140,140,0,0)` | 完全一致 | **0** ✅ |
| 4 | 球的模型坐标 | `cx_model = cx_orig×scale + pad.left` | vb1: `(310.8, 250.3)` | `(310.7, 250.4)` | **0.1 px** ✅ |

> 💡 **为什么它最强**：因为它验证的不是"程序没崩"，而是**"程序算出了数学上正确的值"**。
> 一个数字**精确命中手算值**，比 100 行日志都有说服力。

### V4 · `min/max/real` 统计 —— 冒烟检查

| 项 | 说明 |
|---|---|
| **是什么** | 每帧遍历输出数组，统计 int8 的最小/最大值，并反量化成实数 |
| **验证什么** | 数据**量纲**是否正确；缓冲区里到底有没有数据 |
| **怎么读** | 见下表 |
| **边界** | 🔴 **无法证明"输入影响了输出"** —— 随机数据也会覆盖整个量程 |

| 症状 | 病因 |
|---|---|
| `size` = 期望值的 **4 倍** | `want_float` 设成了 1 |
| `size` 对但 `min=max=0` | `buf` 没填，或空 `Mat` |
| `min=max=-128` | 输入图纯色（全同一值），或 `buf` 指向全 0 内存 |
| `real max > 1.0` | `zp`/`scale` 取错 |
| `min=-128, max=127` | 正常（覆盖全量程） |

> 🔴 **实测教训**：我们曾用 `min/max` 验证 B5，
> 结果**两张完全不同的图片打出了完全一样的统计量** —— 这暴露了它的能力边界。
> 于是才有 V5。

### V5 · FNV-1a `hash` 校验和

| 项 | 说明 |
|---|---|
| **是什么** | 对整个输出缓冲区算一个 32 位哈希（FNV-1a），打印成 8 位十六进制 |
| **验证什么** | ① **因果链**（换输入 → 输出是否变）② **确定性**（同输入 → 输出是否稳定）③ **绑核不影响结果** |
| **成本** | ~0（和 `min/max` 共用同一次遍历） |
| **怎么读** | 比较两次运行的 `hash` 值：**相同 = 输出完全一致；不同 = 输出有差异** |
| **边界** | 碰撞概率 2⁻³² ≈ 2.3×10⁻¹⁰（可忽略）。但它**不能告诉你差异有多大** |

**算法核心**（3 行）：

```cpp
uint32_t h = 2166136261u;              //FNV-1a 初始值（固定常数）
for (...) h = (h ^ (uint8_t)v) * 16777619u;   //异或 + 乘质数，靠无符号回绕做位混合
```

> ⚠️ `(uint8_t)v` 的强制转换**不能省**：`v` 是 `int8_t`（有符号），
> 负数会**符号扩展**成 `0xFFFFFFFF` 再参与运算，导致哈希不稳定。
> 另外必须用 `uint32_t`（有符号溢出是 UB）。

**本工程用过的 3 组对比**：

| 对比 | 结果 | 结论 |
|---|---|---|
| 同一张图连跑 10 帧 | `873539f5` / `a5357af4` / `2ea201f0` **帧帧相同** | ✅ 推理**确定性** |
| 两张不同的图 | `873539f5…` vs `c51f3fec…` **全部不同** | ✅ **因果链打通** |
| `mask=1` vs `mask=7` | 三个 hash **完全相同** | ✅ **绑核只影响性能，不影响结果** |

### V6 · `[time]` 计时

| 项 | 说明 |
|---|---|
| **是什么** | `cv::getTickCount()` 差值 / `getTickFrequency()` → 毫秒 |
| **验证什么** | 每个环节的耗时 vs **性能预算** |
| **怎么读** | 见下表 |
| **边界** | 🔴 **受 CPU/NPU 动态调频影响** —— 必须配合 V8（定频）才可信 |

$$\text{毫秒} = \frac{\text{tick 差} \times 1000}{\text{tick frequency}}$$

**我们测的三个量**：

| 计时项 | 含义 | 实测（640×480） | 预算 |
|---|---|---|---|
| `preprocess` | letterbox 耗时 | **0.11 ms** | — |
| `run` | `rknn_run` 墙钟时间（**含 CPU 侧开销，不只是 NPU 计算**） | **27.6 ms**（单实例单核） | — |
| `[post]` | 后处理耗时 | **0.032 ms** | ≤ 2.4 ms |

**吞吐公式**：

$$\text{吞吐} = \frac{3}{\text{run} + \text{post} + \text{其他}} \qquad \text{延迟} = \text{单帧时间} + \text{排队}$$

### V7 · A/B 对照实验

| 项 | 说明 |
|---|---|
| **是什么** | **只改一个变量**，其余全部相同，比较两组结果 |
| **验证什么** | 那个变量**是否真的有效**，以及**效果有多大** |
| **怎么读** | 差异远大于噪声 → 有效；差异在噪声量级 → 无效 |
| **边界** | 🔴 **必须保证其他条件一致**（否则会得出假结论 —— 见 4.4 陷阱 1） |

**本工程做过的 3 组 A/B**：

| 实验 | 自变量 | 对照组 | 结果 |
|---|---|---|---|
| **ne 核绑定** | `mask=1` vs `mask=7` | 同一张图、同一模型 | 27.6 vs 27.1 ms → **1.8%，无效果** |
| **多实例并行** | 3 实例 vs 1 实例 | 同上 | **120 fps vs 36 fps** → **有效** |
| **实例分布** | 3 实例分 3 核 vs 挤 1 核 | 同上 | 120.3 vs 41.9 fps → **必须分核** |

> ⭐ **第 2、3 组的交叉验证**：
> - 挤 1 核：`71.6/3 = 23.87 ms/帧` → **41.9 fps/核**
> - 分 3 核：`120.3/3 = 40.1 fps/核`
> **两者一致 → 证明 3 核真的在并行**（没有隐性串行）
>
> 这种"**用对照组互相印证**"比单看一个数字可信得多。

### V8 · 定频

| 项 | 说明 |
|---|---|
| **是什么** | 把 CPU / NPU 的频率锁定在最高档，禁止动态调频 |
| **验证什么** | **消除无关变量**，让测量可复现 |
| **怎么读** | 定频后数据应**高度稳定**（帧间波动 < 1ms） |
| **边界** | ⚠️ **重启后失效**；功耗/发热显著上升 |

```bash
sudo sh -c 'for p in 0 4 6; do echo performance > /sys/devices/system/cpu/cpufreq/policy$p/scaling_governor; done; echo performance > /sys/class/devfreq/fdab0000.npu/governor'
```

| 项 | 定频前 | 定频后 |
|---|---|---|
| 单实例 `run`（640×480） | 32.1 ms | **27.6 ms**（稳定 ±0.2） |
| 单实例 `run`（2880×1800） | 27.7 ms | 23.2 ms |
| 三核 `run`（640×480） | 21 → 27 漂移 | **27.1 ms**（稳定 ±0.05） |

> 🔴 **没有定频，任何性能结论都不可信。** 这是我们从一次错误中换来的教训（见 4.4 陷阱 1）。

### V9 · 分布统计（离线数据分析）

| 项 | 说明 |
|---|---|
| **是什么** | 在 PC 上统计数据集里**目标尺寸的分布**（从 YOLO 标注反算像素尺寸） |
| **验证什么** | 模型的**适用边界**：训练集见过多大的目标？部署时的目标在不在这个范围内？ |
| **怎么读** | 对比"部署时目标尺寸"和"训练集分布" —— **超出下限就有风险** |

|---|---|---|

| 5% | **19.5 px** | 20~40 px：**30.5%** |

### V10 · 与标注对比（精度验证）

| 项 | 说明 |
|---|---|
| **是什么** | 用带**真值标注**的图片跑检测，比较"检测出的球心/半径" vs "标注的球心/半径" |
| **验证什么** | **真实精度**（不是"看起来像"，而是"误差多少像素"） |
| **怎么读** | 误差中位数 / 90% 分位 / 漏检率 |
| **边界** | 标注本身有误差（通常 ±2~5 px）<br>val 集分布 ≠ 部署分布 |

**数据来源**：`D:\qq_tenct\data_split_output5\data_split_output\val\`
（223 张图 + 223 个标注文件，YOLO 格式 `class cx cy w h`，全部归一化到 0~1）

**已用于验证的 3 张图**：

| 文件 | 尺寸 | 标注 | 换算后（原图） |
|---|---|---|---|
| `vb1.jpg` | 720×1280 | `0 0.474306 0.391016 0.059722 0.039844` | 球心 (341.5, 500.5)，直径 43×51 px |
| `vb2.jpg` | 1706×1279 | `0 0.482415 0.329554 0.467761 0.630962` | 球心 (823.0, 421.5)，直径 798×807 px |
| `vb3.jpg` | 1279×1706 | `0 0.524629 0.366354 0.564504 0.431419` | 球心 (671.0, 625.0)，直径 722×736 px |

**标注 → 像素的换算公式**：

$$x_{px} = cx_{norm} \times W \qquad y_{px} = cy_{norm} \times H \qquad w_{px} = w_{norm} \times W \qquad h_{px} = h_{norm} \times H$$

> ⚠️ **注意**：`w` 乘**图片宽**，`h` 乘**图片高** —— 因为归一化是分别按宽高做的。

### V11 · 自测工具（假模型）—— B8-2 新增

| 项 | 说明 |
|---|---|
| **是什么** | 用「假模型」（test double）把模板类**真实实例化**，构造可控并发场景做断言 |
| **验证什么** | 并发行为的**正确性**（不是性能）；同时也是模板代码的**编译检查器** |
| **成本** | 写工具一次（`src/pool_selftest.cc`），每次回归 ~1 秒 |
| **怎么读** | T1/T2/T3 各自 PASS/FAIL；退出码 0 = 全过 |
| **边界** | 假模型 ≠ 真模型：验证的是**池的管路**（拷贝/队列/锁），不验证 RKNN 推理本身 |

**为什么必须用「假模型」**：真模型 22ms 不可控、输出无法精确断言；
假模型让「输入内容」和「推理耗时」都成为旋钮，才能构造出**可判定**的场景。
手法：① sleep 放大竞态窗口；② `atomic` 计数数"工作是否真的发生"；③ 覆写原图检验深拷贝。

## 4.4 🔴 七个测量陷阱（**都是真实踩过的**）

### 陷阱 1：不定频就下结论 → 得出完全相反的结论

**发生了什么**：未定频时测得 `mask=1` 是 32.1 ms、`mask=7` 是 21.0 ms → 得出"三核提速 **1.53×**，推荐用 1 实例绑 3 核"。

**定频后重测**：`mask=1` = 27.6 ms、`mask=7` = 27.1 ms → **只差 1.8%，等于没效果**。

**根本原因**：`ondemand` governor 在 CPU 空闲时降频，拖慢了 `rknn_run` 里的 **CPU 侧开销**。
两次实验的 CPU 负载不同（一次在跑 `cv::resize`，一次几乎空闲）→ 频率不同 → 数据不可比。

**教训**：**测任何性能数据前先定频。**

---

### 陷阱 2：以为 `run` 是"纯 NPU 时间"

**真相**：`rknn_run` 的**墙钟时间** = NPU 计算 + CPU 侧开销（ioctl 提交 / DMA 配置 / 等完成）。

**证据**：
- 单实例独占 1 核：27.6 ms → 36.2 fps
- 3 实例抢 1 核：23.87 ms/帧 → **41.9 fps**（**反而更高**）

**原因**：多实例时，一个 context 的 CPU 开销可以与其他 context 的 NPU 计算**重叠**。

**教训**：
- `run` 的绝对值包含了 CPU 开销，**不能当成纯 NPU 算力指标**
- 多实例不仅提吞吐，还能**掩盖 CPU 侧开销**

---

### 陷阱 3：用错测试素材 → 得出错误的瓶颈判断

**发生了什么**：用 1706×1279 的数据集图片测 `preprocess`，得到 **5~6 ms**，一度以为是瓶颈。

**真相**：那只是**图片太大**（`cv::resize` 要读 6.5 MB，超过 CPU L2）。
用户实际的 640×480 场景 `scale = 1.0`，**跳过 resize**，只需 **0.11 ms**（差 **50 倍**）。

**教训**：**测试素材必须贴近真实部署场景**，否则测出来的"瓶颈"是假的。

---

### 陷阱 4：`min/max` 看起来能用，其实证明不了因果

**发生了什么**：B5 用 `min/max` 验证链路，两张**完全不同**的图片都打出 `int8[-128,127] real[0,1]`。

**真相**：随机/垃圾数据**同样会覆盖整个量程**，所以 `min/max` 无法区分"正确输出"和"垃圾数据"。

**解法**：加 FNV-1a `hash`（V5），同一次遍历同时算三个统计量，成本为零。

**教训**：**每个统计量都有能力边界，要问"如果它是错的，这个数字会不一样吗？"**

---

### 陷阱 5：数值巧合掩盖语义错误

**发生了什么**：`vb_head_t heads[VB_ANCHOR_NUM]` —— 数组长度用了"anchor 数"而不是"检测头数"。

**真相**：两者**恰好都等于 3**，所以**编译通过、运行也正确**，编译器**不会给任何警告**。
但如果以后某个模型每头有 5 个 anchor，就会**数组越界**。

**教训**：**数组长度要由"这个数组装的是什么"决定，而不是"哪个宏恰好等于我要的数"。**

---

### 陷阱 6：函数写了但**没被调用** → 编译器完全不报错

**发生了什么**：B7-3 的 `vb_to_original()` 写好了、声明了、编译通过，
但 `infer()` 里**从来没有调用它**。

**症状极其隐晦**：
- ✅ 编译**完全通过**（函数已定义、已声明）
- ✅ 运行**不报错**（`result.balls` 是空 `vector` → 循环不执行 → **静默无输出**）
- ❌ 既不崩溃也不警告，只是结果无从谈起

**是怎么发现的**：靠 V10（标注对比）—— 发现
$$\frac{\text{检测值}}{\text{标注真值}} = \frac{857.0}{320.0} = \frac{1036.0}{391.8} = \frac{975.5}{366.9} \approx \mathbf{2.666} = \frac{1}{scale}$$
**一个恒定的比例因子，直接把问题锁定到"坐标没除以为 scale"。**

**教训（双向）**：
1. **写改动文档时**：新增函数必须同时写明"**在哪里调用它**" —— 否则"写了没调用"是静默失败
2. **排查时**：**一个恒定的比例/偏移量 = 某一级变换没做**。多看几个样本、算算比值，比盯着单张图快得多

---

### 陷阱 7：被「实时时钟」节流的循环 —— 数字看着正常，其实测的是**播放速度**

**发生了什么**：视频模式跑 300 帧，`read` 平均 10.13 ms、`infer` 23.10 ms，
看起来"read 就是解码成本"。但三次重复实验里，`read+infer` 的**和恒等于 33.23 ms** —— 这个"恒定和"暴露了真相。

**真相**：OpenCV 4.2 的 GStreamer **文件模式**默认按影片时间戳实时播放（sink 的 `sync` 默认开），
循环周期 = **影片帧间隔**（10.0 s / 300 帧 ≈ 33.2 ms）。`read` 只是"等下一帧到点"的余量（`read ≈ 33.2 − infer`）。

**判别实验（两次就能分辨）**：

| 实验 | 结果 | 说明 |
|---|---|---|
| 纯 `gst-launch` `sync=false` | 300 帧 **1550 ms**（5.2 ms/帧） | 解码真实吞吐 |
| 纯 `gst-launch` `sync=true` | **10111 ms**（33.7 ms/帧） | 实时节流的样子 |
| demo 默认（文件路径） | 循环和 **33.23 ms/帧** | = 节流 ✅ |
| demo 自定义 pipeline `sync=false` | `read` **0.11 ms**，循环 **24.0 ms/帧** | 解除 ✅ |

**教训**：
1. ⭐ **多个运行里"恒定不变的和" = 有外部时钟在钉节奏** —— 先怀疑节流/限速，
   不要把每个分量的数值当成独立的性能数据
2. 凡是用"视频播放"当输入的性能测量，先问：**它是不是在按实时速度喂我？**
3. 解除方法：给 OpenCV 传**完整 pipeline 字符串**并显式 `sync=false`（见公式手册 §7.6）
