# 🔬 调试与实验方法论

> **这份文档记录的不是"结论"，而是"怎么得出这些结论"。**
>
> 结论会过时（比如 "~~三核提速 1.53×~~" 就是错的），但**方法不会**。
> 你以后遇到的 bug 一定不是这些 bug，但**它们的"形状"会重复出现**。
>
> 每个案例固定写五件事：
> **① 现象 → ② 我当时在想什么 → ③ 凭什么这么想（知识依据）→ ④ 做了什么实验 → ⑤ 结果与教训**

## 0. 为什么要有这份文档

一个 bug 修好了，你会记住"那个 bug 是 XX 原因"。
但真正值钱的是：**"我是怎么一步步逼出这个原因的"**。

因为下次你面对的是**另一个** bug，但**推理路径是同一条**。

> 📌 这份文档和《验证与测量手册》的分工：
> - 《验证与测量手册》= **有哪些手段**（V1~V10、陷阱清单）
> - 本文档 = **怎么用这些手段去逼出真相**（推理过程）

## 1. 性能工作的固定套路

```
测量 → 拆解 → 定位 → 优化 → 再测量
  ↑                            │
  └────────────────────────────┘
```

**四个阶段缺一不可**，而且顺序不能变：

| 阶段 | 在做什么 | 做错了会怎样 |
|---|---|---|
| **测量** | 拿到可信的数字 | 🔴 后面全错（"三核 1.53×"就是这么来的） |
| **拆解** | 把总时间分成若干段 | 不知道优化谁 |
| **定位** | 找出最长的那一段 | 优化了不重要的地方 |
| **优化** | 只针对瓶颈动手 | 白费力气 |

> ⚠️ **跳步的代价**：直接"看着代码猜哪里慢" → 改了半天，帧率没动。

## 2. 六条核心原则

### 2.1 没有数据不许优化

**反面教材**：B7 之前以为"预处理肯定很慢，该上 RGA 硬件加速"。
**实测**：`preprocess` 只有 **0.11 ms**（占 110fps 预算的 0.4%）。

$$\text{优化一个占 0.4\% 的东西，最好结果就是快 0.4\%}$$

**你要先知道"谁慢"，才能知道"优化谁"。**

---

### 2.2 拆解优于总时间

**只知道"一帧 45ms"→ 你打算优化哪里？不知道。**

拆开之后：

| 阶段 | 耗时 | 结论 |
|---|---|---|
| `read` | 11.5 ms | 有戏 |
| `infer` | 31.1 ms | **大头在这** |
| `draw` | 0.1 ms | 噪声 |
| `write` | 0.0 ms | 没写 |

**一眼看出该打谁。**

#### 🔧 怎么落地：在代码里埋"分段计时"

```cpp
int64_t t = cv::getTickCount();
do_something();
stat.add((cv::getTickCount() - t) * 1000.0 / cv::getTickFrequency());
```

**关键**：`getTickFrequency()` 是**每秒多少 tick**（板子上约 24 MHz），
所以 `tick 差值 × 1000 / freq` = **毫秒**。

---

### 2.3 控制变量：一次只改一个

**反面教材**：B6 的"实验 1 vs 实验 3"——
同为单核、同计算量，`run` 差了 4.4 ms。当时不知道多了什么变量。

**正确做法**：改 A 之前，把 B、C、D 钉死。

**本工程的"必须钉死清单"**（每次测性能前检查）：

| # | 要钉死的 | 命令 / 位置 |
|---|---|---|
| 1 | CPU 3 个 policy | `/sys/devices/system/cpu/cpufreq/policy{0,4,6}/scaling_governor` = `performance` |
| 2 | NPU devfreq | `/sys/class/devfreq/fdab0000.npu/governor` = `performance` |
| 3 | **DMC（内存控制器）** | `/sys/class/devfreq/dmc/governor` = `performance` ← **最容易漏！** |
| 4 | 线程绑核 | `taskset -c 4-7`（大核） |
| 5 | 输出不刷屏 | 重定向到文件，或 `--quiet` |
| 6 | 温度 | `grep . /sys/class/thermal/thermal_zone*/temp`（>70°C 要警惕） |

> 🔴 **重启后 1~3 全部失效**，每次测性能前重做一遍。

---

### 2.4 做**可证伪**的预测：互斥假设 + 判别实验

**核心思路**：先列出**互相排斥**的假设，再设计一个**能让它们给出相反结果**的实验。

#### 正例：`read` 那 11ms 到底是什么？

| 假设 | BMP 应该 | 实测 | 判定 |
|---|---|---|---|
| 是**磁盘 IO** | 慢 11.8 倍 ≈ **130 ms** | 2.59 ms | ❌ 排除 |
| 是**JPEG 解码** | 快，≈ 0.5~1 ms | 2.59 ms | ✅ 成立 |

**文件大 11.8 倍、耗时变成 1/4.4** —— 两个假设的预测差 **200 倍，无法混淆**。

$$\text{好的判别实验} = \text{把假设之间的差距放大到"不可能看错"}$$

#### 反例：只说"我觉得是 A"

"我觉得是 JPEG 解码慢" —— 这不是假设，这是**猜想**。
**猜想不能证伪，也不能证真。**

#### 🔧 落地模板

```
假设 1：______   → 预测看到 ______
假设 2：______   → 预测看到 ______
两个预测在 ______ 上完全相反
实验：只改 ______，其它全不动
```

---

### 2.5 看**形状**，不只看数字

`run` 的 `min=27.4 / max=29.6` —— 这**一个数字对**对应三种完全不同的原因：

| 形状 | 长什么样 | 常见原因 |
|---|---|---|
| **台阶** | 一直 A，某一刻跳到 B，然后一直是 B | **频率/状态切换**、模式改变 |
| **单调漂移** | 慢慢变大（或变小），不停 | 热降频、资源泄漏、缓存失效 |
| **随机抖动** | 上下跳，无规律 | 调度、中断、其他进程干扰 |
| **双峰** | 只有 A 和 B 两个值 | 两条代码路径 / 两档频率 |

#### 正例：帧 14~46 的完整形状

```
帧 014~023   0.09 / 27.6   ← 平台 1（极稳，±0.05）
帧 024        0.10 / 28.3   ← 开始动
帧 025~028   0.32 / 27.5   ← ⚠️ "隆起"
帧 029~030   0.18 / 29.4   ← 跳上去了
帧 030+      0.17 / 29.4   ← 平台 2（也很稳）
```

**"平台 1 → 隆起 → 平台 2"这个形状，直接排除了"热降频"**（温度只有 33°C），
并且指向"某种状态切换 + 迁移过程"。

> **只看 `min/max` 你会以为"有抖动"；看到形状你才知道"是跳了一级"。**

#### 🔧 落地：怎么拿到形状

`min/max/avg` **三个数字不够** —— 要有**逐帧序列**。
所以每帧把值 `printf` 出来，重定向到文件，再抽样看。

### 2.6 **比值**比绝对值信息量大

**绝对值的困惑**：`preprocess` 从 0.094 变成 0.175 —— 是快了还是慢了？为什么？

**比值是"指纹"**：

$$\frac{0.175}{0.094} = \mathbf{1.86 \approx 2}$$

**"×2"这个数字一定有来源：**

| 什么变成 2 倍 | 会让 CPU 上的代码慢约 |
|---|---|
| CPU 频率减半 | 2× |
| 从 A76 大核换到 A55 小核 | **2.0~2.5×**（频率比 0.798 × IPC 比 1.6~2） |
| 内存频率减半 | 取决于是不是内存受限 |

**实测 1.86 → 落在"大核换小核"的区间里** ✅

> ⭐ **遇到"干净的整数比"（×2、×4、÷3），先别当成巧合 ——
> 那通常是某个硬件档位的比值。**

## 3. 六种高级技巧

### 3.1 反推：用方程组解出**不能直接测**的量

**问题**：`rknn_run` 内部 = NPU 计算 + CPU 侧开销。这俩**没法分开测**（SDK 不提供）。

**办法**：让 CPU 侧开销单独变一次，就能解出来。

设 $T_{\text{npu}}$ = NPU 计算时间，$T_{\text{cpu}}$ = CPU 侧开销，$k$ = CPU 慢化倍数。

两次测量（同一份代码、同一个模型，只是 CPU 快慢不同）：

$$\begin{cases} T_{\text{npu}} + T_{\text{cpu}} = 27.61\\ T_{\text{npu}} + k\,T_{\text{cpu}} = 29.35\end{cases}$$

**$k$ 从哪来？** 从 `preprocess`（纯 CPU）身上量：$k = 1.86$。

**解出来**：

$$T_{\text{cpu}} = \frac{29.35-27.61}{k-1} = \frac{1.74}{0.86} \approx \mathbf{2.0\ ms}\qquad T_{\text{npu}} \approx \mathbf{25.6\ ms}$$

> ⭐ **核心思想：想测一个测不到的量，就找一个"只影响它"的旋钮，
> 拧一下，用两次测量的差值反推。**

---

### 3.2 交叉验证：一部分数据拟合，另一部分**验证**

**错误做法**：拿 4 个点拟合 4 个参数 → 完美吻合 → 以为自己发现了规律。

**正确做法**：

| 步骤 | 做法 |
|---|---|
| 拟合 | 只用 vb640 + vb1280 两个点，解出两个参数 |
| **验证** | 拿 vb1 和 (67) —— **没参与拟合**的点 —— 去检验 |

结果：

$$t_{\text{imread}}[\text{ms}] \approx 7.5\times10^{-6}\cdot N_{px} + 16.8\times10^{-6}\cdot N_{B}$$

| 图 | 预测 | 实测 | 误差 |
|---|---|---|---|
| `vb1.jpg` | 10.42 | 10.30 | **+1.2%** |
| `(67).jpg` | 19.59 | 19.67 | **−0.4%** |

**拟合点是"背答案"，验证点才是真本事。**

---

### 3.3 极值（`min` / `max`）比均值信息量大

| 统计量 | 看什么 |
|---|---|
| `avg` | 整体水平 |
| `min` | **这台机器最好能跑多快** = 优化天花板 |
| `max` | **最坏情况** = 实时性的真正敌人 |

**为什么 `max` 对实时系统特别重要**：

> 平均值会把"偶尔卡一下"抹掉。而**实时系统最怕的正是那"偶尔一次"的 200ms**
> —— 球已经飞过去了。

---

### 3.4 诚实命名：给计时点起对名字

**反例**：我们把 `cv::imread` 那一段叫 `read`。

$$\texttt{cv::imread} = \underbrace{\text{读文件字节}}_{\text{0.3\%}} + \underbrace{\text{JPEG 解码}}_{\text{99.7\%}}$$

**名字叫 `read` → 脑子自动归到"IO 开销" → 优化方向想成"换更快的存储"。**

**真实方向是"换更小的图"或"用硬件解码器"。**

> ⭐ **一个名字起窄了，会把你引到完全错误的优化方向上去 —— 而且你还觉得自己推理得很对。**

---

### 3.5 造对照组：只改一个**无关的维度**

**问题**：怎么证明那 10ms 是解码而不是 IO？

**难处**：改尺寸的话，IO 和解码**同时**变化，分不开。

**解法**：找一个"只改 IO、不改解码"的维度 —— **换格式**。

| 文件 | 格式 | 大小 | 解码工作量 |
|---|---|---|---|
| `vb1.jpg` | JPEG | 229 KB | 大 |
| `vb1.bmp` | BMP | **2.64 MB** | **≈ 0** |

**IO 变差（文件更大），解码变好（不用解码）→ 两个假设给出相反方向的预测。**

> ⭐ **设计对照组的关键：找一个"只影响其中一个假设"的变量。**

---

### 3.6 用**恒定比值**定位坐标系错误

**现象**（B7-3）：程序不报错，但 `result.balls` **永远为空**。

**关键线索**：把"检测值"和"真值"做比值 —— 得到 **2.666**，而且**每一帧都是 2.666**。

$$2.666 = \frac{1}{0.375}$$

而 $0.375$ **正好是那张图的 letterbox 缩放比**。

> ## ⭐ 恒定比值 = 坐标系错误的指纹
> 如果只是"算错了"，比值会乱七八糟。
> **比值恒定**说明"整体差了一个固定的缩放/平移" → **坐标变换没做，或者做反了**。
> 顺着这个线索就找到了：`infer()` 里**漏了调用 `vb_to_original()`**。

**这类"恒定偏差"还可以是**：
- 恒定比例 → 缩放没做 / 做反
- 恒定偏移 → 平移没做 / 做反
- 正负号反 → 坐标轴方向

### 案例 3 · 三核 1.53× —— 一个**假结论**

| | |
|---|---|
| **现象** | 不定频测得 `run`：32.1 ms（单核）vs 21.0 ms（三核）→ 看起来提速 **1.53×** |

| **教训** | 🎯 **测任何性能数据前，必须先钉死所有频率。**<br>🎯 **被证伪的结论要"划掉并保留"，不要删** —— 否则以后还会被同一批假数据误导 |

### 案例 7 · 从"×1.86"反推出"CPU 被换到小核了"

| | |
|---|---|
| **现象** | `preprocess` 从 0.094 ms 跳到 0.175 ms（`run` 只涨了 6.3%） |
| **思路** | **这个比值太"干净"了**：$0.175/0.094 = 1.86 \approx 2$。干净比值 → 硬件档位 |
| **知识依据** | ① `preprocess` 是**纯 CPU** 图像处理（`copyMakeBorder` + 内存搬运）→ 变慢只能是 CPU 变慢<br>② 板子 CPU 布局：policy0 = A55×4 @1.8GHz；policy4/6 = A76×4 @2.256GHz<br>③ **A76 的 IPC 约为 A55 的 1.6~2 倍**<br>④ 综合慢化 $\approx \frac{1}{0.798}\times(1.6\sim2) = 2.0\sim2.5$ ✅ 与 1.86 吻合 |
| **实验** | `taskset -c 4-7`（钉死在大核）→ **台阶完全消失** |
| **教训** | 🎯 **"×2"这种干净比值一定是某个硬件档位的比值。**<br>🎯 **一个量变化时，要同时看"受它影响的"和"不受它影响的"另一个量**：<br>`preprocess`（纯 CPU）变了 86%，`run`（NPU 为主）只变 6.3% → 说明**不是 NPU 变慢，是 CPU 变慢** |

### 案例 8 · `dmc` 漏定频 —— 定频清单必须**写下来**

| | |
|---|---|
| **现象** | 查系统状态时发现 `dmc`（内存控制器）governor = `dmc_ondemand`，频率 **528 MHz**（**最低档**） |
| **思路** | "定频"这件事本身要**系统性地检查**，不能凭印象说"我定过了" |
| **知识依据** | `ls /sys/class/devfreq/` 列出**所有**频率可变的设备。<br>板子上有 4 个：**npu / dmc / gpu /（还有一个）** —— 我们只定了 npu |
| **实验** | `echo performance > /sys/class/devfreq/dmc/governor` → 528 → **2112 MHz** |
| **结果** | `run` **27.6 → 22.44 ms（−19%）**；`read` 波动从 **3.74 ms → 0.48 ms** |
| **教训** | 🎯 **"定频"不是一件事，是一个清单**。写进文档，每次照着做。<br>🎯 **内存带宽是 NPU 推理的隐藏瓶颈** —— NPU 算力再强，数据搬不快也得等 |

### 案例 9 · PowerShell 引号地狱

| | |
|---|---|
| **现象** | `bash: 行 1: 语法错误: 未预期的文件结尾` |
| **思路** | ssh 传命令经过 **三层**引号解析：<br>**PowerShell** → **`ssh.exe`** → **远程 bash** |
| **知识依据** | 每一层都会"吃掉"或"展开"某些字符（`"`、`$`、`(`、`)`、`[`、`]`） |
| **解法** | **base64**：本地写好 bash 脚本 → base64 编码 → `ssh board "echo <b64> \| base64 -d \| bash"`。<br>base64 字母表只有 `[A-Za-z0-9+/=]`，**三层规则一个都不会碰它** |
| **教训** | 🎯 **能不用引号就不用**：`grep time` 而不是 `grep '\[time\]'`<br>🎯 实在不行就 **base64**，一次到位 |

### 案例 10 · "未解疑点"日后会自己拼起来

| | |
|---|---|
| **旧记录** | B6 时写下："同为单核、同计算量，**2880 图（23.2 ms）比 640×480 图（27.6 ms）快 4.4 ms**。怀疑与 DDR 频率有关，**未验证**" |

### 案例 11 · 预测高了 7%：忘了「并行不是免费的」

| | |
|---|---|
| **现象** | 单实例 `run` = 22.44 ms → 我预测 3 实例吞吐 $= 3/22.44 =$ **133.5 fps**；实测 **124.9 fps** |
| **错在哪** | 把"$3 \times$ 单实例"当成了上限。**并行不是免费的。** |
| **知识依据** | ① 并行共享**内存带宽**（而 NPU 推理是带宽受限的 —— 案例 8）<br>② 4 颗大核要同时供 3 个 worker 的 CPU 侧开销 |
| **实验** | `bench_throughput` 三组：3 核各一 / 3 个挤 1 核 / `dup` vs `indep` |
| **结果** | 并行效率 $\eta = 124.9/(3\times44.6) = \mathbf{93.3\%}$ |
| **教训** | 🎯 **算"理论上限"时，必须问：这个上限被什么共享资源限制？**<br>🎯 93.3% 其实是**好成绩**，但**一定要把效率算出来**，才知道还剩多少空间 |

### 案例 12 · 用「对照组」验证**测试工具本身**

| | |
|---|---|
| **现象** | 新写的 `bench_throughput`，**怎么知道它测得对不对？** |
| **思路** | **跑一个"能心算出答案"的场景** —— 把 3 个实例全挤到同一个 NPU 核上 |
| **知识依据** | 如果核是串行资源，$k$ 个实例挤一核应该**正好慢 $k$ 倍**（可从单实例 `run` 预测） |
| **实验** | `RKNN_CORE_MASK=1 ./bench_throughput ... 3 300 dup` |
| **结果** | 三个 worker 耗时 **67.21 / 67.21 / 67.21 ms**，而 $67.21/3 = 22.40 \approx$ 单实例 `run` **22.44 ms** |
| **教训** | 🎯 **新写一个测量工具时，先跑一个"能心算出答案"的场景。**<br>🎯 这一步还顺便把 B6.6 的 41.9 fps 对照组复现了（44.6 fps）→ **两代工具可比**，新数据可信 |

## 6. 速查表：现象 → 第一反应

| 现象 | 第一反应（先怀疑什么） |
|---|---|
| 编译通过但不工作 | **数据流的下游**：函数调了吗？返回值用了吗？（案例 2） |
| `Usage` / 用法提示 | **参数校验那一行**，不是使用处（案例 1） |
| 检测值/真值 = **恒定常数** | **坐标变换没做或做反**（案例 2/§3.6） |
| 候选框 = 0 | 先怀疑**输入内容**（尺寸/纵横比/颜色），再怀疑代码（案例 5） |
| 性能数据**不可复现** | **有没有定频**（案例 3/8） |
| `run` 值出现**干净整数比** | **硬件档位**（频率/核/内存）（案例 7/§2.6） |
| 前几帧慢、后面快 | **预热**（分配器 / page cache / 缓存） |
| 一直 A，某刻跳 B，然后一直 B | **台阶** → 状态或频率切换（案例 6/7/8） |
| 慢慢变大不停 | **热降频 / 资源泄漏** |
| 上下乱跳无规律 | **调度 / 中断 / 其他进程** |
| `bash: ... 语法错误` | **引号分层问题** → base64（案例 9） |
| 预测和实测差很远 | **先怀疑自己的心智模型**，不要先怀疑数据（案例 4） |

## 7. 一句话总结

> ## 调试的本质，是**把"我觉得"变成"我测出来"**
>
> - **我觉得**预处理慢 → **我测出来**它只占 0.4%
> - **我觉得**是磁盘 IO → **我测出来**是 JPEG 解码
> - **我觉得**三核提速 1.53× → **我测出来**只有 1.8%
> - **我觉得**是热降频 → **我测出来**温度只有 33°C
> - **我觉得**定频定过了 → **我测出来**漏了 dmc
>
> **每把"我觉得"换成一个数字，你就离真相近一步。**
