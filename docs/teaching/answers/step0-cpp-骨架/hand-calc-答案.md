# step0 · 手算答案（对照 `step0-cpp-骨架/hand-calc.md`）

## 题 1（§6.1 复现）

$$\text{吞吐} = \frac{N\times1000}{T_{\text{单帧}}} = \frac{3\times1000}{22.44+0.043} \approx \frac{3000}{22.483} \approx \mathbf{133.4\ fps}$$

并行效率 = 实测 ÷ 理论 = $124.9 / 133.4 \approx \mathbf{93.6\%}$。

差额（≈6%）去哪了：3 个实例共享**内存带宽**（DMC）+ 4 颗大核还要同时供 3 个 worker 的 CPU 侧准备开销。（00 §6 C 结论 3）

## 题 2（§6.1 变式）

$$N \times \frac{1000}{22.5} \ge 110 \;\Rightarrow\; N \ge \frac{110\times22.5}{1000} = \mathbf{2.475}$$

- 2 个：$2000/22.5 \approx 88.9$ fps ✗（<110）
- 3 个：$\approx 133$ fps ✓（考虑 93% 效率后 ≈124，仍 >110）

**结论：它就是"保 110fps 必须用满 3 个 NPU 核"的算术证明。**

## 题 3（§6.4 复现）

1. 各环节上限：采集 109.5 / 推理上限 ≈132 / 结果侧实际 ≈96.2。
   **最短板是"结果循环侧"**——由喂料间隙 + 采集与推理抢 CPU 构成，**不是 NPU 本身**。
2. $109.5-96.2 \approx 13.3$ fps 的差额主要来自：
   - 采集线程自身的 read+解码开销与节拍（约 9.1 ms/帧）；
   - 结果循环"一进一出"的节拍与 1 ms 睡眠量化（00 §6 O：全速 106 vs worker 上限 125 差额同源）；
   - 显示/落盘虽已解耦，仍占少量 CPU。

## 题 4（§6.4 变式）

- 90 fps：$3\times1000/30 = \mathbf{100\ fps}$ ✓（余量 11%）
- 110 fps：需要 $N \ge 110\times30/1000 = \mathbf{3.3}$ 个 → **3 核不够**（100 < 110）。
  出路：降输入分辨率、换更小模型、多板级联——RK3588S 只有 3 个 NPU 核，单机无解。

## 题 5（§7.2 复现）

$$t \approx 7.5\times10^{-6}\times307200 + 16.8\times10^{-6}\times38304 = 2.304 + 0.644 \approx \mathbf{2.95\ ms}$$

对照实测 **2.90 ms** → 误差约 **−1.6%**（两点拟合经验式，2% 内属正常）。

## 题 6（§7.3 变式）

1. $1.2\times10^6 \div 0.105\times10^{-3} \approx 1.14\times10^{10}$ B/s ≈ **11.4 GB/s**。
2. $0.9\times10^6 \div 0.30\times10^{-3} \approx 3.0\times10^{9}$ B/s ≈ **3.0 GB/s**。
   低的原因：这 0.30 ms 里含 **~0.2~0.3 ms 的每次调用固定开销**（ioctl 提交 + 同步等待），
   小拷贝下固定开销占大头；而 `inputs_set` 是纯内存拷贝，没有硬件作业调度开销。
   （B10 结论：RGA 适合"大图/链路搬运"，不适合高频小任务——见《B10优化验证报告》§3.2）

## 题 7（§7.2 变式）

字节项：$16.8\times10^{-6}\times229376 \approx 3.85$ ms；
剩余 $11.5-3.85 = 7.65$ ms 由像素项贡献 → $N_{px} \approx 7.65 / 7.5\times10^{-6} \approx \mathbf{1.02\ Mpx}$。
最接近的常见分辨率：**720×1280 = 921.6K px**（本题数据就取自 vb1，误差在经验式正常范围）。

## 题 8（§7.3 复现）

$5.3\times10^6 \div 2.59\times10^{-3} \approx 2.05\times10^{9}$ B/s ≈ **2.0 GB/s**（与 00 §6 I 的反推值一致）。
