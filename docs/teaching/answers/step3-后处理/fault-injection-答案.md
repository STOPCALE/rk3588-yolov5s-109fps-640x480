## 故障 · 候选消失

**根因（一句话）**：取数函数把内存布局当成了 **channel-last `[H,W,18]`**
（`(i·W+j)·18 + 6a+f`），而真实布局是 **`[3,6,H,W]` plane 结构**（`(6a+f)·G + i·W + j`）——
植入的 obj 永远读不到，预筛全灭 → 候选=0。

**参考排查路径**：
1. 先确认"植入确实发生了"：植入方用的是**文档布局**，正确定位到
   `(6·0+4)·6400 + 30·80 + 38 = 28038`，`buf[28038]` 就是 112（obj 的 q 值）。
2. 再打印程序**实际**扫到的下标：`field_idx(0,4,30,38) = (30·80+38)·18 + 4 = 43888` ——
   两个数根本不是一回事 ⇒ 索引公式错了。
3. 那两个伪候选也不是巧合，都能对上账：
   - `(a=0,i=23,j=73)`：它的 obj 下标恰好算到 **34438** —— 那是植入的**类分数**（127）被当成了 obj；
   - `(a=1,i=10,j=46)`：obj 下标恰好算到 **15238** —— 那是植入的**宽高**（54，真实值 0.71）被当成了 obj。
   周围取到的坐标字段则全是 −128 → 解出来 `cx` 只由 j 贡献、`r=0`、`prop=0`。
   **能解释每个伪候选的来历 = 真正看懂了布局。**
4. 对照手册 §1.2：anchor 在最外层、字段居中、行列最内 → 正确式 `(6a+f)·G + i·W + j`。

**修复（一行）**：

```c
return (6 * a + f) * G + i * W + j;   // 原：(i*W + j) * 18 + 6*a + f（错）
```

**验证**：重跑 → `candidates=1  ball@(311.0, 250.0)  r≈11.7  prop≈0.941`，伪候选消失。

**为什么"既不崩也不报错"**：错误下标算出来仍是**合法缓冲区内地址**（只是指到了别的格子），
读到的都是别的"合法但无意义"的值。
**这类"合法地址 + 错误含义"的 bug 只能靠手算对照抓出来**——也正是 B7-1 用 r 误差 3.8% 反向
验证 anchor 匹配的同一套方法论。
