# step5 · 故障注入答案（对照 `step5-多线程流水线/fault-injection.md`）

---

## 故障 1 · 帧被偷换

**根因（一句话）**：队列里保存的是**共享缓冲的浅拷贝**（"帧头"进队、像素还是同一块内存），
主线程提交后立刻复用缓冲覆写 → worker 睡（假推理）醒来读到的已是**别人的数据**。

**参考排查路径**：
1. `tag mismatch` 几乎 100% → 先怀疑"读到的不是提交时的内容"。
2. 在主线程提交后打印 `buf[0]`、worker 读取前再打印 —— 值已被改成 `0xAA`（复用标记）。
3. 结论：**谁拥有像素**——所有权没转移，两个线程共用了同一块内存。

**修复（语义 = cloneInput 深拷贝）**：提交时复制：

```cpp
Frame owned;                    // 池内保存的帧
owned.data.assign(src.data.begin(), src.data.end());   // 深拷贝
```

**验证**：重跑 → `mismatch = 0`（对照 T1：100 帧、提交后立刻覆写，不一致 0）。

**为什么真实工程里是"随机错乱"而不是"稳定错"**：错不错、错多少，取决于
"主线程覆写"和"worker 读取"的**时序**——这正是数据竞争的特征，也注定它**必被 T1 这类
"强制覆写"的测试**才能稳定抓住。

## 故障 2 · 流水线串行化

**根因（一句话）**：主循环用了**阻塞版 `get()`** —— "喂一帧、等一帧"，
在途恒为 1，3 个 worker 里只有 1 个在工作（吞吐=单帧速率）。

**参考排查路径**：
1. 阻塞模式吞吐 ≈ 41~42 fps ≈ $1000/24$ ms → 命中"单帧速率"特征 → 怀疑并行度没用上。
2. 对照同一程序里的非阻塞取法：120+ fps —— 差异只在"取结果"的那一行。
3. 数在途：阻塞模式 pending 峰值恒为 1。

**修复（在循环侧）**：改用非阻塞 `get_try()`；把"已完成的未来"批量收集：

```cpp
while (pool.get_try(result)) { /* 统计/画框，不阻塞 */ }
```

**验证**：重跑 → 吞吐 **≥110 fps**（真实工程：42.5 → 103+，工具对照一致）。

**工程含义**：并发系统里 **"等结果"必须与"喂任务"解耦**；
"喂一帧等一帧"把并行流水线退回成串行——而且从代码上看"只差一行"。
