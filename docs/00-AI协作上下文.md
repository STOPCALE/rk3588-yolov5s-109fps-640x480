## 1. 一句话项目

在 **Orange Pi 5（RK3588S）** 上，用 **YOLOv5 + NPU** 做**排球实时检测与跟踪**，
为 **RC 排球机器人**提供排球的**中心坐标 + 半径**，供上位机做弹道解算与自动接球。
语言 **C++14 / CMake**；PC 开发 + 开发板编译验证。

## 4. ⭐ 应用场景与性能目标（**最重要的一节**）

### 场景参数

| 项 | 值 |
|---|---|
| 目标 | **排球**（单类模型），直径 ≈ **21 cm** |
| 场地 | 对面底线 → 我方底线，水平距离 **18 m** |
| 飞行时间 | **≈ 2 秒** |
| 轨迹 | 抛物线（抛体运动） |
| 视角 | 机器人**第一视角** |
| 检测输出 | 排球的**中心坐标 + 半径**（上位机做数学解算） |
| 机器人用途 | 自动接球 |

### 弹道推算

| 量 | 推算值 | 依据 |
|---|---|---|
| 水平速度 | **≈ 9 m/s** | 18 m ÷ 2 s |
| 初始垂直速度 | ≈ 9.8 m/s | 对称抛物线，上升 1 s |
| 最高点 | ≈ 4.9 m | ½·g·t² |
| 合速度范围 | **9 ~ 13.3 m/s** | 顶点最小，发射点最大 |

### ⭐ 为什么必须 90-110 fps（**有物理依据，不是拍脑袋**）

| 帧率 | 帧间隔 | 球移动距离 @9 m/s | 相对球直径(21 cm) |
|---|---|---|---|
| **30 fps** | 33.3 ms | **30 cm** | **1.43 倍** ← 相邻两帧的球完全不重叠，连续跟踪失效 |
| 60 fps | 16.7 ms | 15 cm | 0.71 倍 |
| **90 fps** | 11.1 ms | **10 cm** | 0.48 倍 |
| **110 fps** | 9.1 ms | **8.2 cm** | 0.39 倍 |

**两条独立的理由**：

1. **跟踪连续性**：30 fps 时球在两帧之间位移 **1.4 个球径** → 无法建立帧间对应关系
2. **运动模糊**：若曝光时间 ≈ 帧间隔，30 fps 下球会拖成 **30 cm 长的模糊带** → **根本检测不到**；
   90 fps 下拖影 ≈ 半个球径，仍可检测

### 🔴 用户明确要求（**不要替他"简化"**）

- ⚠️ **不能因为"落点预测只需要几帧"就降低帧率要求**
- 需要**高帧率 + 高实时性**来做**球位置的连续跟踪控制**
- 落点预测**只用于前馈 + 点位到达**，不是唯一目的
- 目标：**90 fps 保底，希望达到 110 fps**

### ⭐ "实时性"的准确定义（用户原话）

> "实时推理得到的结果，要和**显示的行动相差不大**，不能像原工程一样，
> 说是 100 帧，结果运行结果和现实运动**差很多**"

**→ 用户要的是【端到端延迟小】，不是【帧率高】。**

原工程的症状：帧率数字不低，但每个结果都是**几百毫秒前**的画面 → "和现实运动差很多"。

**延迟来源与对策**（B8 要做的事）：

| 延迟来源 | 量级 | 对策 |
|---|---|---|
| **V4L2 驱动缓冲** | **最多 133 ms** | `cap.set(cv::CAP_PROP_BUFFERSIZE, 1)` |
| **在途帧积压** | **无上界** | `setMaxPending(1~2)` 丢弃陈旧帧，给延迟**上界** |
| **`imshow` 阻塞主循环** | 几十 ms | 显示移到独立线程，只写"最新帧槽" |

$$L_{\min} = \underbrace{1/fps_{\text{摄像头}}}_{采集} + \underbrace{24.9\text{ms}}_{推理} + \underbrace{\le 2.4\text{ms}}_{后处理} \approx \mathbf{37\text{ ms}}\ (\text{100fps 摄像头})$$

- 37 ms 里，13 m/s 的球移动 **48 cm**（≈2.3 个球径）
- ⭐ **延迟可以被弹道模型补偿** —— 排球是抛体运动，只要延迟**稳定且已知**，
  就能用 $p_{now} = p_{t-L} + vL + \frac12 aL^2$ 外推回"现在"，等效零延迟
- 🔴 **真正致命的是"延迟不稳定"**（原工程那样从 30ms 涨到 800ms）→ **根本无法补偿**
- **所以目标不是"延迟为零"，而是：延迟小 + 稳定 + 可测量**

### ⚠️ 关键约束：球在图像里非常小（**待确认摄像头 FOV**）

假设水平 FOV = 60°、分辨率 640 px 宽 → 每米像素数 = `640 / (1.155 × d)`

| 距离 | 视野宽度 | 球直径像素（21 cm） |
|---|---|---|
| 18 m | 20.8 m | **≈ 6.5 px** |
| 12 m | 13.9 m | ≈ 9.7 px |
| 9 m | 10.4 m | ≈ 13 px |
| 6 m | 6.9 m | ≈ 19 px |
| 3 m | 3.5 m | ≈ 39 px |
| 1.5 m | 1.7 m | ≈ 78 px |

**推论：球在大部分轨迹上只有 6~15 px —— 这是典型的小目标检测问题。**

**因此：绝不能为了提帧率而缩小模型输入分辨率**（480×640 → 球 5~12 px；320×320 → 球 3~7 px，基本检测不到）。

> ❓ **待确认**：实际摄像头的型号、分辨率、帧率、FOV、安装角度。这直接决定上表。
> 若球太小，可选方案是**提高摄像头分辨率**（1280×720 → 球 ≈ 13 px）或**换更窄 FOV 的镜头**。

## 6. ⭐ 关键测量数据（**未定频**，含 ±15% 漂移）

`best.rknn` @640×640，**10 帧循环的稳态值**：

#### A. 单实例、**未定频**（🔴 数据不可信，仅作反面教材）

| 实验 | 图 | core mask | `preprocess` | `run` |
|---|---|---|---|---|
| 1 | 640×480 | `1`（单核） | **0.24 ms** | **32.1 ms** |
| 2 | 640×480 | `7`（三核） | 0.11~0.32 ms | **≈ 21.0 ms** |
| 3 | 2880×1800 | `1`（单核） | 7.4 ms | **27.7 ms** |

> 🔴 **这批数据把 AI 误导过**：据此得出"三核提速 1.53×，推荐 1 实例绑 3 核"。
> 定频后证明**完全是假的** —— 是 `ondemand` governor 的 DVFS 漂移污染了测量。
> **教训：拿测量数据下结论前，必须先确认系统状态稳定（定频）。**

#### B. 单实例、**已定频**（✅ 可信）

| 实验 | 图 | core mask | `preprocess` | `run` | 稳定性 |
|---|---|---|---|---|---|
| 1 | 640×480 | `1`（单核） | **0.11 ms** | **27.6 ms** | 27.55~27.78 |
| 2 | 640×480 | `7`（三核） | **0.11 ms** | **27.1 ms** | 27.05~27.12 |
| 3 | 2880×1800 | `1`（单核） | 1.1~1.8 ms | 23.2 ms | 22.2~23.6 |

- **结论：三核绑核对单模型无收益**（27.6 → 27.1，仅 1.8%，等于噪声）
- ⚠️ 未解疑点：同为单核、同计算量，2880 图（23.2ms）比 640×480 图（27.6ms）**快 4.4ms**。
  怀疑与 DDR 频率（`dmc` devfreq）有关，未验证。**但不影响设计结论**

#### C. ⭐ 3 实例并行、已定频（✅ **决定性数据**）

| 配置 | 各 worker 平均 infer | **总吞吐** | 判定 |
|---|---|---|---|
| **3 独立实例，各绑 1 核** | 23.3 / 26.4 / 25.1 ms | **120.3 fps** | ✅ 90 & 110 双达标 |
| **3 实例 `dup_context` 共享权重** | 23.8 / 24.2 / 25.4 ms | **122.6 fps** | ✅ 90 & 110 双达标 |
| 3 实例**全挤核 0**（对照组） | 71.6 ms × 3 | **41.9 fps** | ❌ |

**三个关键结论**：

1. ✅ **90 fps 与 110 fps 双双达标** —— 用**现有 640×640 模型**，**不需要重转模型**
2. ✅ **`dup_context` 可以绑到不同核** —— 122.6 ≈ 120.3 fps，说明共享权重的 3 个实例
   能真正在 3 个核上并行 → **`rknnPool` 的共享权重方案可行**（审计问题 P1 解除）
3. ⭐ **单核真实能力 ≈ 41.9 fps**（即 23.9 ms/帧纯 NPU 计算）
   而且**多 context 抢同一核反而提高利用率**（41.9 vs 单实例独占的 36.2 fps）——
   因为一个 context 的 CPU 侧准备（ioctl/DMA）可以与其他 context 的 NPU 计算**重叠**

**三个结论**：

1. ✅ **模型能检测到球**：`prop = 0.67~0.89`（阈值仅 0.25），`head=0`（stride 8，符合小球预期）
2. ✅ **anchor 匹配**：`r` 只差 3.8% → `best.rknn` 用的就是 **YOLOv5 标准 anchor**
   （旧工程那组硬编码值 **可以放心沿用**）
3. ✅ **整数预筛效果超预期**：151200 个格子 → 只剩 **15 个候选**，耗时 **0.032 ms**
   - 原因：`-O3` 把 `if (obj < thres_i8) continue;` **自动向量化**（一次比 16 个 int8）
   - 且 151200 字节只有 148 KB，**完全装进 CPU L2 缓存**
   - ⭐ **这就是 Ch04 后处理的设计核心**：先做最便宜的整数筛选，再对极少数候选做昂贵的浮点解码。
     若把 151200 个格子全部反量化，耗时会高**几百倍**

**⚠️ 待解决**：15 个候选**来自同一个球**（相邻格 + 多个 anchor 都激活）→ 需要 **NMS 合并**（B7-2）

### 已确认的结论

1. ~~三核绑核有效：32.1 → 21.0 ms，提速 1.53×~~ → 🔴 **错的！**
   定频后实测只有 1.8%（= 噪声）。**三核绑核对单模型无收益**。
   真正有效的是**多实例并行**：3 实例 → **120 fps**
2. **letterbox 内跳过 resize 生效**：2880 图 7.4 ms vs 640×480 图 0.24 ms（**差约 30 倍**）
3. **校验和（FNV-1a）证明链路正确**：
   - 同图 10 帧 `hash` **完全相同** → 推理确定性 ✅（无并发污染、无未初始化读）
   - 不同图 `hash` **完全不同** → 输入确实影响输出 ✅
   - `mask=1` 与 `mask=7` 的 `hash` **相同** → 绑核只影响性能、不影响结果 ✅
4. **数据漂移元凶 = `ondemand` governor**：
   实验 1 vs 3 同为单核、同计算量，`run` 却差 4.4 ms。
   机制：CPU 空闲降频 → 拖慢 `rknn_run` 的**CPU 侧开销**（ioctl 提交 / DMA 配置 / 等待完成）
5. **帧率 ≠ 延迟**（核心概念）：
   - 并行**只能提高帧率**，**完全不能降低延迟**
   - 延迟下限 = 单帧推理时间 + 一帧采集时间

## 7. 性能目标可行性分析（初步）

$$\text{吞吐} = \frac{3 \times 0.9}{\text{单核单帧时间}} \qquad\qquad \text{延迟} = \text{单帧时间} + \text{排队等待}$$

| 方案 | 总吞吐 | 单帧延迟 | 90 fps? | 110 fps? |
|---|---|---|---|---|
| 1 实例绑 3 核 | 36 fps | 27.6 ms | ❌ | ❌ |
| **3 实例各绑 1 核（640×640，已实测）** | **120.3 fps** | **24.9 ms** | ✅ | ✅ |
| 3 实例 `dup_context`（已实测） | 122.6 fps | 24.5 ms | ✅ | ✅ |
| ~~模型转 640×480~~ | ~~预估 130 fps~~ | — | — | ❌ **不需要了** |

> ⭐ **结论：现有 640×640 模型已经达标，不需要重新转换模型。**
> 之前"必须转 640×480"的判断是基于**未定频的假数据**得出的，已作废。

### ⚠️ 后处理预算（Ch04 的硬约束，**必须严格控制**）

$$\text{每帧可用时间} = \frac{3}{\text{目标吞吐}} \qquad \text{后处理预算} = \text{每帧可用时间} - 24.9\text{ ms(infer)}$$

| 目标 | 每帧可用 | **后处理 + 其他开销必须 ≤** |
|---|---|---|
| **110 fps** | 27.3 ms | **2.4 ms** ⚠️ 极紧 |
| 100 fps | 30.0 ms | 5.1 ms |
| **90 fps** | 33.3 ms | **8.4 ms** ✅ 宽松 |

**Ch04 的后处理写法必须围绕这个预算设计**：
- 用 **int8 整数比较**预筛（不反量化全部 151200 个格子）
- 只对少数候选框做浮点解码
- 单类模型的 NMS 极简（**无跨类比较**）

### 端到端延迟估算（不含显示）

```
11 ms  采集（@90fps 一帧）
 0.2 ms 预处理
28 ms  推理（单核，3 实例并行时每帧仍是 28ms）
 2 ms  后处理（NMS）
-------
≈ 41 ms  感知链路下限
```

**"零延迟"物理上不存在。** 要压到更低只能缩小模型 —— 而那会牺牲小目标精度。

## 8. 硬性约束（不要改）

| 约束 | 原因 |
|---|---|
| `cmake_minimum_required(VERSION 3.16)` 不能提高 | 板子只有 3.16.3 |
| `CMAKE_INSTALL_RPATH` 必须是 `$ORIGIN/lib` | 绝对路径换目录失效；相对 CWD 的 `lib` 必须 `cd` 才能跑 |
| `install(DIRECTORY model DESTINATION .)` 末尾**不加斜杠** | 加了会丢 `model/` 层，而代码硬编码了 `./model/coco_80_labels_list.txt` |
| `CMAKE_BUILD_TYPE` 必须有默认值 | 否则静默变 `-O0` |
| OpenCV 组件按"符号所在的库"选 | `highgui.hpp` 会间接 include `videoio.hpp`，容易"编译过、链接炸" |
| 关机必须 `sync && sudo poweroff` 并等指示灯灭 | ext4 writeback，直接断电会零填充文件（**已损坏 Git 仓库两次**） |
| `.ps1` 必须纯 ASCII 或 UTF-8 **带 BOM** | PS 5.1 把无 BOM 的当 GBK 读 → 中文乱码 → 语法错误 |
| 同步只能用 Git，**不用 `scp` 传源码** | 会漏文件 / 覆盖 / 无历史 |
| 板子上永不 `git commit` / 编辑源码 | 只 `git pull --ff-only`，保证不分叉 |
